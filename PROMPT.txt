工艺组选精馏塔时，真正拍板的那一步现在这套后端还接不住：最少理论板、最小回流比它都能算，可选型会上真正要回答的是"回流和板数怎么折中"——回流比压低一点、塔就得做高（板数多、设备贵）；板数压下来、回流就得抬上去（能耗高、操作费贵）。这条此消彼长的权衡曲线，正是拿最少板数和最小回流比当两个渐近端点张出来的，工程上用 Gilliland 关联把它描出来。现在这层还没有，我想补上，让选型的人能在这条曲线上来回定点。

要加的能力围绕 Gilliland 关联这一条经验曲线展开，它把两个已经无量纲化的量绑在一起：横坐标 X = (R − Rmin)/(R + 1) 衡量回流比比最小回流比宽裕多少，纵坐标 Y = (N − Nmin)/(N + 1) 衡量实际板数比最少板数多用了几成，两者由一条单调的经验关系 Y = f(X) 连起来（X 从 0 走到 1，Y 从 1 单调降到 0，这条关系式在整个服务里钉死一份、各处引用同一套）。这里的 Nmin、Rmin 就是现有服务已经用 Fenske、Underwood 算出来的那两个量，你要直接调用现成那两处逻辑拿到它们，别为这个功能重推一遍最少板数或最小回流比的公式。

补两条能用起来的路径。其一，给定实际回流比 R，算出对应的理论板数 N：先用现有 Underwood 逻辑拿到 Rmin，由 R 与 Rmin 组出横坐标 X，代进 Gilliland 关系读出 Y，再连同现有 Fenske 逻辑拿到的 Nmin 把纵坐标 Y 解回板数 N。其二，反过来，给定工程上愿意接受的理论板数 N，反求需要多大的实际回流比 R：由 N 与 Nmin 组出纵坐标 Y，在 Gilliland 关系上反查横坐标 X（Y 随 X 单调，反查有唯一解，别用一味二分闷头找，单调性摆在那儿利用起来又快又稳），再由 X 与 Rmin 解回 R。这两条路径共用同一条 Gilliland 关系式和同一套 Nmin/Rmin，不允许一条正着读曲线、一条另拿一套近似式反着凑，导致同一个设计点正反算出两个对不上的结果。

要守住的自洽性检验，验收会逐条验。两条路径必须能闭合：给一个合法的 R 正向读出 N，再把这个 N 反求回去得到的 R，必须和最初的 R 在容差内吻合；反过来给 N 求 R、再拿 R 求 N 也要闭合回原来的 N。两个渐近端点要落对：当实际回流比趋近最小回流比（X 趋近 0）时，所需板数应当急剧上升、趋于很大（Y 趋近 1，塔要做得很高才够）；当实际回流比放得很宽裕（X 趋近 1）时，板数应当逼近最少理论板 Nmin（Y 趋近 0）。单调关系也要成立：把实际回流比一路调大，反算出的所需板数应当单调下降、绝不回升——这正是"回流换板数"的物理含义，要在好几组回流比下都验得过。

碰到算不出来的工况，得回一个讲清缘由的结构化错误，不能闷头返回一个凑数的板数。分三类：实际回流比 R 小于或等于最小回流比 Rmin，此时 X 落到 0 或为负，权衡曲线上根本没有对应的有限板数，这是"回流不足以支撑任何有限塔高"，要点破而不是硬给一个数；反求路径里给定的目标板数 N 不大于最少理论板 Nmin，比理论下限还少，物理上做不到，拒掉；至于进料组成、目标组成、相对挥发度这些底层参数本身越界的，现有接口已经在校验，这层顺着走、不重复造轮子。

对外新增 HTTP 接口暴露这两条路径（给 R 求 N、给 N 求 R），沿用现在只走 HTTP、无网页界面的方式。工程上把 Gilliland 关联与这条曲线上的正读、反查求根单独拆成一个能独立测的模块，别塞进现成的 Fenske/Underwood 或逐板阶梯文件里，也别破坏现有那三样输出（最小回流比、最少理论板、逐板阶梯）的行为。补一组自动化测试钉住：给 R 求 N 与给 N 求 R 两条路径正反闭合、回流比趋近 Rmin 时板数趋于很大、回流比很宽裕时板数逼近 Nmin、增大回流比所需板数单调下降、以及上面三类非法输入分别落到对应的结构化失败。技术栈仍是 Java 17 加 Spring Boot；打包走两段式，前一段拿 JDK 17 的 Maven 镜像把可执行包编出来，后一段换成精简的 JRE 17 镜像加载它，两段合在一个 Dockerfile 里一遍构建通过。
